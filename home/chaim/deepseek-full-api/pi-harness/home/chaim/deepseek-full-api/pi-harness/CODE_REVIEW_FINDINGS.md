 Deep Dive: Stream Adapters — pi-harness**Date:** 2026-05-27 | **Reviewed:** `deepseek-web-stream.ts` (321 lines), `deepseek-native-stream.ts` (316 lines), plus context from `xml-toolcall-parser.ts`, `agent-loop.ts`, `web-api-client.ts`---## Architecture OverviewThe streaming adapter layer sits between the DeepSeek API and the agent loop, responsible for:. **Establishing** an SSE/stream connection to DeepSeek (web or native API). **Parsing** the raw SSE byte stream into structured events. **Detecting** tool calls embedded in XML within the text stream. **Reconstructing** the assistant message with tool calls separated from text. **Emitting** events to the agent loop (`text`, `toolCall`, `done`, `error`)Two implementations exist for the same interface: `deepseek-web-stream.ts` — scrapes the DeepSeek web chat (chat.deepseek.com) by reverse-engineering their internal API `deepseek-native-stream.ts` — uses the official DeepSeek API (api.deepseek.com) with an API key---## 1. `deepseek-web-stream.ts` (321 lines) — Web API Adapter### HIGH: Token-based auth with no refresh mechanism```typescriptlet token = state.deepseekToken || process.env.DEEPSEEK_TOKEN;if (!token) throw new Error("No DeepSeek auth token found...");```The token is loaded once at startup. If it expires mid-session, all subsequent requests fail with `WafTokenExpiredError` or `StaleAuthError`. There's no automatic token refresh, no retry with re-auth, and no user-facing prompt to update the token.**Severity: HIGH.** A long-running agent session will silently break when the web token expires (~hours). Fix: detect auth errors and either auto-refresh (if a refresh token exists) or emit an `auth_expired` event the UI can handle.### MEDIUM: XML parser initialization can fail silently```typescripttry {await batchParser.init(); catch (e: any) {console.error(`[DEBUG] XML parser init failed:`, e.message);}```The WASM-based XML parser (`xml-toolcall-parser.ts`) is initialized asynchronously. If it fails, the code continues — tool calls embedded in the stream will never be parsed. The agent will see raw XML as text and get confused.**Severity: MEDIUM.** If `init()` fails, the stream adapter should either fall back to regex-based parsing or refuse to start with a clear error.### MEDIUM: `fetch()` with no timeout on the SSE connection```typescriptconst resp = await fetch(apiUrl, { method: "POST", headers, body: JSON.stringify(payload) });if (!resp.body) throw new Error("No response body from DeepSeek web API");```The `fetch()` call has no `AbortSignal` timeout. If the DeepSeek server accepts the connection but never sends data (hanging), the agent hangs forever. The `ReadableStream` reader will wait indefinitely for the next chunk.**Severity: MEDIUM.** Add an `AbortSignal.timeout()` or a wrapper that kills the connection after N seconds of inactivity.### LOW: Hardcoded polling interval for deep think```typescriptawait new Promise((r) => setTimeout(r, 1000));```After sending a message, the web adapter polls every second for the response. This adds 1s latency to every agent turn. The polling interval is not configurable.**Severity: LOW.** Consider exponential backoff or WebSocket-based push when available.### MEDIUM: Cookie-based session management is brittle```typescriptheaders: {"Cookie": `session=${token}`,"X-Requested-With": "XMLHttpRequest",...}```The web adapter mimics a browser session with hardcoded headers. If DeepSeek changes their CSRF protection, adds CAPTCHA challenges, or modifies their internal API, the entire adapter breaks. There's no feature detection or graceful degradation.**Severity: MEDIUM.** Document that this is inherently fragile. Add a health-check endpoint that validates the session is still active.### LOW: `console.error` scattered throughout instead of structured logging```typescriptconsole.error(`[DEBUG] XML parser init failed:`, e.message);console.error("[deepseek-web] API error:", data);```ses raw `console.error` instead of the `log()` utility used elsewhere in the codebase. These messages don't appear in structured logs and can't be filtered by level.**Severity: LOW.** Replace with the `log()` utility for consistency.---## 2. `deepseek-native-stream.ts` (316 lines) — Native API Adapter### HIGH: API key in plaintext environment variable```typescriptconst apiKey = state.deepseekApiKey || process.env.DEEPSEEK_API_KEY;```Same pattern as the web adapter — no key rotation, no vault integration. If the key leaks (e.g., via `ps aux` showing environment), the account is compromised.**Severity: HIGH.** Add support for reading the key from a file (`DEEPSEEK_API_KEY_FILE`) or a keychain. At minimum, redact the key from logs.### MEDIUM: XML tool call parsing blocks the stream reader```typescriptconst parser = new XMLStreamParser();// ... inside the read loop:parser.feed(chunk);```The XML parser processes chunks as they arrive from the SSE stream. If the LLM generates a very long tool call (e.g., a large `write` operation), the parser buffers all of it in memory before emitting the `toolCall` event. This blocks the read loop and delays subsequent text events.**Severity: MEDIUM.** The XML parser should emit partial tool call events or stream arguments as they arrive, rather than waiting for the closing tag.### MEDIUM: `toolCall` and `done` events use `as any` type assertions```typescriptstream.push({ type: "done", reason: doneReason, message: assistant } as any);```The stream event types are not properly typed. The `as any` cast circumvents TypeScript checking, so adding a field to the done event would not produce a compile error in consumers.**Severity: MEDIUM.** Define a proper discriminated union type for stream events: `StreamEvent = TextEvent | ToolCallEvent | DoneEvent | ErrorEvent`.### LOW: Text block state machine is hand-rolled```typescriptlet currentTextBlock = "";let inTextBlock = false;function flushTextBlock() { ... }function appendText(text: string) { ... }```The adapter maintains its own state machine for grouping text tokens into blocks. This duplicates logic that exists elsewhere. A `TextBlockAccumulator` abstraction shared between both adapters would reduce duplication.**Severity: LOW.** Extract shared text-block management into a utility.### LOW: `stopReason` string comparison for flow control```typescriptconst doneReason = emittedToolCalls > 0 ? "toolUse" : "stop";```Using string literals for control flow is fragile — a typo like `"tooluse"` would silently break the agent's loop. Use an enum or const object.**Severity: LOW.** Define `enum StopReason { ToolUse = "toolUse", Stop = "stop", Error = "error" }`.---## 3. Shared Concerns (Both Adapters)### HIGH: Both adapters use the same XML tool-call parserBoth adapters depend on `xml-toolcall-parser.ts` which requires WASM initialization (`batchParser.init()`). This creates a single point of failure: If WASM fails to load (blocked by CSP, missing file, incompatible Node version), **both** adapters break The parser is a module-level singleton — no way to have separate instances for web vs native Tool calls embedded in XML that don't match the expected schema are silently dropped**Severity: HIGH.** Add a pure-JS fallback parser (regex-based) that handles 90% of tool call patterns. Use the WASM parser for the remaining edge cases.### MEDIUM: No common interface between the two adaptersBoth adapters export a `stream()` function but with slightly different signatures and return types. There's no `StreamAdapter` interface that both implement:```typescript// deepseek-web-stream.tsexport function streamDeepSeekWeb(state: HarnessState): StreamFn// deepseek-native-stream.ts  export function streamDeepSeekNative(state: HarnessState): StreamFn```They happen to be compatible by coincidence, not by contract. Adding a new required field to one adapter's output would silently break consumers using the other.**Severity: MEDIUM.** Define a `StreamAdapter` interface with `stream(messages, tools, signal): AsyncIterable`.### MEDIUM: Tool call results are not streamed back incrementallyBoth adapters buffer the entire LLM response (text + tool calls) before emitting any events. For a response with 4 tool calls and 2000 tokens of text, the user sees nothing until the entire response is complete. This feels slow.**Severity: MEDIUM.** Emit text tokens as they arrive. Only buffer tool calls until the closing tag.### LOW: No metrics or observability hooksNeither adapter emits metrics on: Time to first token (TTFB) Tokens per second Tool call count per response Parse errors per session Connection drops and retries**Severity: LOW.** Add optional `onMetrics` callback for performance monitoring.### LOW: Both adapters hardcode model names```typescript// deepseek-native-stream.tsconst model = state.model || "deepseek-chat";// deepseek-web-stream.tsconst model = "deepseek_v3"; // hardcoded```The web adapter hardcodes the model while the native adapter reads from state. This inconsistency means switching models requires code changes for web but config changes for native.**Severity: LOW.** Make both adapters read the model from `state.model`.---## 4.
